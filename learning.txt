Learn these in this order
1. Ground truth / test-set creation — essential

Before metrics, learn:

What is a ground-truth relevance set
Train/test split
Query → relevant documents
How to create test queries
Avoiding data leakage
Why you need multiple queries/users rather than judging 3–4 examples manually

For your current system, this is the foundation.

Example:

Query:
"mind-bending science fiction"

Expected relevant:
[Inception, Interstellar, Arrival, ...]

Then your system returns:

[Inception, Avatar, ...]

Now you have something objective to compare.

2. Precision@K

Learn this first.

Of the top K results I returned, how many were relevant?

For example:

Top 5:
✓ ✓ ✗ ✓ ✗

Precision@5 = 3/5 = 0.60

This directly answers:

"Are my results good?"

3. Recall@K

Then learn:

Of all the relevant items available, how many did I retrieve?

This tells you whether your retriever is missing relevant content.

Precision and recall together are particularly important for your retrieval pipeline.

4. NDCG@K

This is very important for your system because ranking matters.

Suppose both systems retrieve the same relevant movies:

System A:
Relevant
Relevant
Irrelevant
Irrelevant

System B:
Irrelevant
Irrelevant
Relevant
Relevant

Precision could be identical, but System A has the useful results earlier.

NDCG captures that.

Learn:

relevance grades
DCG
IDCG
normalization
why position matters
5. MRR

Learn this after NDCG.

MRR asks roughly:

How high is the first relevant result?

This is particularly useful for queries where the user expects an obvious result quickly.

7. Error analysis — extremely important

This is the part that answers your "how do I improve it?" question.

Learn how to inspect failures and categorize them.

For example:

Wrong result
     ↓
Why?
 ├── semantic retrieval failure
 ├── BM25 failure
 ├── RRF failure
 ├── reranker failure
 ├── metadata failure
 └── LLM query-understanding failure

Then you know what to change instead of randomly tuning the system.

This is arguably more useful to you right now than learning additional metrics.

8. LLM structured-output evaluation

Once you add your LLM query-understanding layer, learn:

Field-level accuracy
Exact match
Constraint extraction accuracy
Invalid/malformed output rate
Evaluation against a manually created gold dataset

Example:

User:
"Give me sci-fi movies after 2015 without horror"

Expected:
genres_include = ["sci-fi"]
genres_exclude = ["horror"]
year_min = 2015

LLM:
genres_include = ["sci-fi"]       ✓
genres_exclude = ["horror"]      ✓
year_min = 2015                  ✓

You can measure how reliably the LLM converts natural language into retrieval instructions.

9. Constraint correctness

This deserves its own metric.

For:

"Movies after 2015 without horror"

you need to verify:

Every result:
year > 2015        ✓
horror absent      ✓

This isn't really Precision@K. It's constraint satisfaction/correctness.
